# 2026-10-01 — Headless `codex exec` runs become children of their launcher, and Codex runs finally close

A Claude session in another project ran a script that fanned 49 topics out through `xargs -P 4 … codex exec -C <scratchpad>/gen/work/<topic>`. Every job is a real `codex` process holding a rollout and firing the user-global lifecycle hooks, so the Node daemon minted 49 `codex-cli` sessions named after scratchpad directories (`2020s_ai_hw`, `2030s_future_sw`, …) — four live at a time, rotating through every deck — and 49 APME runs. All 49 runs, plus six from 9/29–9/30, were still open 26 hours after their processes exited: Codex has no `SessionEnd` hook, a codex run closed on nothing else, and the abandoned-run reaper skips every run the collector still holds (`isLiveRun`).

Two changes, both Node-daemon only:

- **A headless run is a child, not a session.** `bridge/src/codex-exec-children.ts` keeps one registry with two producers. The passive observer reads `session_meta.originator: codex_exec` off the rollout and walks the process's ancestry (`timeout` → `node` → `codex`, then `bash` → `xargs` → `run.sh` → `zsh` → `claude`) to another observed session's pid; a run with such an ancestor leaves the roster and is reported as that session's child (`foldHeadlessCodexSessions`). The hook path asks the same registry first: a headless rollout whose parent is visible is attached on its `SessionStart`, one whose process is not in the 5 s process table yet is held out of every parent pipeline as `pending` until the observer or a later hook resolves it, and one nobody launched (the user's own `codex exec` in a terminal) is `standalone` after 60 s and stays a session. Attaching retracts whatever the child's first hooks created (hook row, APME run, hub-driver identity) and hands a `SubagentStart` to the parent's `SubagentTimelineTracker` — the same census a Claude `Agent` call moves, so the parent row shows `subagents: {active, peak, completed}`, the timeline folds the fan-out into one dispatch row, and the parent's active APME task records `sample_events.kind='subagent'`. The child's `Stop` (or its process leaving a non-empty table) is its completion: a `SubagentStop` with the run's last reply, or the topic directory when it said nothing. OTel treats a folded child as hook-owned so the span batch `codex exec` exports at exit cannot re-synthesize the row.
- **A Codex run closes when its session leaves the roster.** `sweepVanishedCodexRuns` (coordination tick, 5 s) tracks every Codex session this daemon holds a run for and closes the run once the id has been absent from observer rows, hook rows and OTel rows for 90 s — longer than one failed `lsof` scan and the 60 s a hook row outlives its Stop. This is the Codex analogue of Kiro's observed-vanish close and OpenClaw's idle close; the abandoned-run reaper remains the restart-only backstop it always was.

Not done here: the Swift daemon. It has the process table (`ProcessEnumerator`, sysctl) and reads `~/.codex`, so the same fold is possible, but it synthesizes Codex rows from hooks alone today and would need the rollout-by-id lookup and the ancestry walk ported; until then the App Store build still shows a headless batch as sessions. The Codex hook snippet also carries no `X-AgentDeck-Pid` header, which is why the hook path matches the process by its `-C <cwd>` argv instead of by pid; adding the header (three mirrored installers plus a migration) would make hook-time attachment exact.
